# 评分方法

[English](scoring.md) · [返回成绩表](../README.zh-CN.md#results)

BenchFS 衡量实际运行行为、代码评审确认的缺陷和可维护性。首页同时展示综合分数及各维度结果。

## 测试通过率与分项得分

通过率按适用测试项计算：

```text
通过率 = (通过 + 符合预期的失败) / 适用项数
适用项数 = 通过 + 符合预期的失败 + 失败 + 非预期通过 + 超时 + 缺少必需功能
```

不适用项不计入分母，超时和缺少必需功能按失败计。测试要求某项操作被拒绝时，符合要求的失败也计为通过。

语义测试、pjdfstest、xfstests、稳健性、崩溃一致性和真实应用采用**类别等权平均**：先计算各类别的通过率，再对有适用项的类别取平均，乘以 100 得到分数。这样，测试数量较多的类别不会仅凭数量占据更大权重。

**磁盘格式使用原生一致性分。** 报告中的检查通过率作为补充统计，不能替代格式分数。构建与 SDK smoke 不参与总分。

## 总分

当前采用 `core-overall-v3-zero-fill`，修订版 `2026-10-04-r2`。每轴先按有理由的自身尺度计分，再直接加权：

```text
总分 = 0.35 × C + 0.20 × R + 0.20 × S + 0.10 × W + 0.10 × P + 0.05 × M
```

| 维度 | 计算方法 | 总分权重 | 子预算理由 |
|---|---|---:|---|
| 正确性 C | 语义 30% + pjdfstest 30% + xfstests 15% + 格式 25% | 35% | 语义保留 75%；重叠的 Linux 回归少于契约测试与广泛 POSIX 操作 |
| 稳健性 R | 稳健性测试 40% + 崩溃分 60% | 20% | 优先持久状态承诺；契约允许的安全拒绝仍计通过 |
| 代码评审 S | 下述 confirmed、按根因去重的缺陷负担曲线 | 20% | 严重度表达损害与范围，不再重复变换 |
| 真实应用 W | 版本管理 25% + 数据库 50% + 归档 25% | 10% | 数据库并发内容与 crash/reopen 各占其预算一半 |
| 性能 P | CPU/NVMe 各半；每项速度 80% + RAM 20% | 10% | 两种设备场景及资源成本均保留固定预算 |
| 可维护性 M | 11 项静态代理共享六类风险预算 | 5% | 相关指标共享预算，语法诊断限制份额 |

移除旧版统一 U。分项表继续展示原生结果，加权后的轴分可能不同于类别等权的 profile 分。本版只重新计量已有证据，给 agent 的标准、生成实现、签认 review 和原始测试结果保持原样。

缺失输入仅在暂计总分中按 0 处理，表中用“—”与实测零分区分；缺失份额仍保留原权重，部分缺失的轴用 `*` 标注。计算保留原始精度，排序使用未舍入总分。诊断证据保持原资格，暂计汇总不等于正式 release 结果。

[新旧总分记录](../results/overall-score-v3.json)保留 v2 总分及输入；[冻结数值参数](../results/scoring-calibration-v3.json)列出完整权重和锚点。数值是工程与政策判断，不是统计拟合出的最优参数。不使用 cohort z-score、同方差归一化或分布缩放；新增其他提交不会改变已有提交的得分。

## 崩溃后的可靠性

**完整测试分**按用例是否满足全部要求计算。**崩溃分**分别计算已验证的能力，并用于稳健性 R：

| 检查项目 | 权重 | 检查内容 |
|---|---:|---|
| 磁盘结构 | 40% | 独立检查磁盘结构是否有效 |
| 数据正确性 | 40% | 检查内容，以及此前承诺保存的数据 |
| 卸载与重开 | 20% | 卸载后磁盘结构须有效，并清除 dirty 标记；已测试的再次打开须成功 |

前两项保护数据，后一项检查正常使用流程。比例在重算前确定，统一用于所有提交。R 仍按稳健性测试 40%、崩溃分 60% 计算；各主轴权重不变。

每个用例的每个项目只计一次。两轮中任一轮失败，该项目就失败；重开后数据改变，数据正确性就失败。G0–G8 等权，每组 24 项。成功卸载后仍有 dirty 标记，只扣该用例的卸载与重开分；磁盘损坏可能同时使磁盘结构和卸载与重开失败。

按规则安全拒绝挂载、且不改动磁盘，也计满足要求；这不表示数据已恢复。未验证的项目保留原权重、计 0，R 标 `*`。前一步失败后未测试的再次打开不计通过，也不取消已有的独立检查结果。首轮未测试与再次打开未测试的计数可能重叠。

原始失败数和完整测试结果保持原样。[r1 分数](../results/overall-score-v3-r1.json)、[r1 参数](../results/scoring-calibration-v3-r1.json)与 [r1 审计](../results/scoring-audit-v3-r1.json)保留供比较。本次只重算已有记录。

## 性能尺度

每个 workload/cache 的生产满分目标取已有 **ext4、XFS、Btrfs 精确速率的固定几何均值**。两种设备场景共用此能力目标；这表示达到生产能力目标的程度，不宣称同设备成对速度实验。生产数据是每单元一次、120 秒窗口；候选保留协议 v2 自适应采样。

```text
生产目标 = geometric_mean(ext4_rate, xfs_rate, btrfs_rate)
速度分 = 100 × clip(log(候选速率 / floor) / log(生产目标 / floor), 0, 1)
```

相同倍率改善得到相同分差。达到组合目标得 100；超过时分数封顶，但原速率保留。组合成员固定，不为每个候选选有利参照；组合目标满分不等于每个成员每项都满分。

速度预算：顺序 I/O 30%、随机 family 40%（single/multi/shared 为 20/10/10%）、同步覆盖 30%；cold/warm 各半。metadata 继续独立诊断。最低目标来自明确的部署政策，独立于候选分布：

| 工作负载 | CPU floor | NVMe floor |
|---|---:|---:|
| 顺序 | 100 MiB/s | 50 MiB/s |
| 随机 single | 1000 IOPS | 500 IOPS |
| 随机 multi | 2000 IOPS | 1000 IOPS |
| 随机 shared | 1000 IOPS | 500 IOPS |
| 同步覆盖 | 50 ops/s | 20 ops/s |

沿用已发布操作包络：顺序最低目标相当于每 GiB 纯传输约 10.24/20.48 秒；并行随机总处理预算至少为 single 的两倍；同步流目标相当于平均每次完成操作 20/50 ms。这些是政策目标，不是测试 deadline，也不是已独立测量的用户需求。同步 operations/s 不等于单独测得的 fsync latency。

RAM 采用绝对分段线性预算：≤512 MiB 得 100，2 GiB 得 50，≥8 GiB 得 0，对应 32 GiB guest 的约 1.56%/6.25%/25%。取留存 candidate cgroup 的最大峰值，包含初始化与驻留计费，不与内核文件系统内存混比。候选失败只使对应速度单元为 0，未测保持缺失；未观察完整 fio 负载时不奖励 RAM。

## 可维护性尺度

`maint-v3-policy` 复用冻结的 `maint-v2-rev5` 原始提取和节点，只改聚合：局部复杂度 30%、架构 10%、重复 15%、unsafe 证明义务 15%、错误路径 20%、工具诊断 10%。unsafe 说明比单纯出现得到更高权重，错误处理代理高于语法 lint。它们是维护风险代理，不是 confirmed 缺陷。

| 代理 | 权重 | 得 100 / 60 / 0 的原始节点 |
|---|---:|---|
| 函数 SLOC p95 | 10% | 40 / 100 / 250 |
| 分支 p95 | 15% | 8 / 15 / 30 |
| 嵌套 p95 | 5% | 3 / 5 / 8 |
| 文件 SLOC p95 | 5% | 600 / 1500 / 3000 |
| 模块循环占比 | 5% | .25 / .50 / .80 |
| 重复率 % | 15% | 3 / 10 / 25 |
| unsafe / KLOC | 5% | 2 / 10 / 30 |
| 无说明 unsafe / KLOC | 10% | 1 / 5 / 15 |
| 错误风险 / KLOC | 20% | 2 / 10 / 30 |
| lint / KLOC | 5% | 1 / 5 / 15 |
| 抑制 / KLOC | 5% | .5 / 2 / 6 |

各项节点间线性插值，节点之外饱和。大小与分支表示局部推理范围，循环表示修改传播，重复表示同步修复位置，unsafe 和错误路径表示证明义务；诊断的预算较小，因为噪声及相关性较多。节点是明确的工程预警区间，尚未用独立维护任务验证精确位置。

## Agent 代码评审

多个 agent 独立审查每个实现，合并重复根因，再通过讨论确认问题和严重度。只有已确认、按根因去重的缺陷计入 S；已驳回或证据不充分的指控不计入。

```text
负担 = 40 × critical + 15 × high + 5 × medium + low
S = 10000 / (100 + 负担)
```

该规则为 `agent-review-score-v2`：负担为 0 时得 100 分，为 100 时得 50 分，为 500 时得 16.67 分。新增缺陷仍会降低分数，但扣分幅度逐渐减小。严重度权重是政策等效关系：5 个 low 根因等效 1 个 medium，3 个 medium 等效 1 个 high，8 个 medium 等效 1 个 critical，不是实测风险概率。scale=100 将 20 个 medium 等效根因锚定为半分。完整审查后没有确认缺陷才得 100 分，这不等于证明实现没有错误；未完成或未开展审查时没有 S 分数，不能当作零缺陷。

首页和单实现报告公开完成状态、各严重度计数与诊断分数；[聚合 JSON](../results/agent-review.json) 还提供不透明的证据 hash。具体缺陷和 agent 对话保留在私有证据中。

## 校准敏感性

当前提交用于审计，不是独立验证集。[聚合审计](../results/scoring-audit-v3.json)保留各轴标准差、covariance、饱和、性能噪声和参数敏感性；现有重复性证据不足以支持分布缩放。敏感性情景中，将 review scale 从 100 改为 200 会使 Opus 第一，所以第一名依赖明确的风险政策。median ± MAD 扰动是描述性检查，不是置信区间。

## 开发统计

开发耗时、token 用量、费用和源码规模分别报告，不参与得分或同分排序。每行模型成绩对应一次开发，而不是多次运行的平均值。模型和编程 agent 共同构成表中的比较对象。
